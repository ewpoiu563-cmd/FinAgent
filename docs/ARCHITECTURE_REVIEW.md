## 总体判断

项目可以称为 **金融任务型 Agent 原型**：模型参与需求拆解、工具必要性与来源规划，工具返回后有充分性检查和局部重试/回退。它已经超过固定的检索加回答流程。

目前自主性主要发生在受限决策点，执行器和恢复路径大多预定义。距离更可靠的 Agent，关键差距是通用的观察→更新状态→调整计划→再执行闭环，以及跨任务数据传递和最终目标验收。换一个 Agent 框架、加入多 Agent 或更多工具，不会直接解决这些问题。

## 框架优点与边界

| 层 | 已有工程价值 | 主要边界 |
|---|---|---|
| Planning | 区分需求、时间、工具必要性与来源，支持结构化状态 | 多次 LLM 决策产生开销；计划失败仍可能进入旧路径 |
| SQL | 语义规划、实体对齐、常见 intent 编译、只读执行 | SQL 可运行不代表时间和统计口径正确 |
| RAG | Dense/BM25/RRF/重排、文档过滤、页码和 chunk 来源 | 四份招股书样本较小；冲突段落及表格口径仍是难点 |
| Web | 事实与多跳路径、抓取、finding 与来源追踪 | 权威披露身份和页面变化仍会影响可靠性 |
| Evidence | 统一证据模型、充分性检查、部分路径的引用校验 | 引用 ID 有效不等于内容支持结论，主任务合成还未统一 |
| Session | Redis、指代补全、压缩且失败保留历史 | 并发、话题切换和历史累积缺少完整控制 |
| Observability | Trace、RunSummary、调用耗时和 usage | 运行 success 不是事实正确；日志隐私与扫描成本有边界 |
| Eval | 历史报告可帮助定位问题 | 按新要求转人工，不再扩展自动评分系统 |

## 优先修复项

优先级：P1 为直接影响复杂任务正确性或实际运行资源的问题；P2 为特定接口、复现和展示问题。网络暴露相关问题在对外部署前需要优先处理。本报告没有将下列项目标为已修复。

### 1. P1：主任务合成仅拼接片段，无法保证最终交付

**代码确认**：`orchestration/task_execution.py:177` 起，在 required 执行任务成功后，SYNTHESIS 使用换行拼接片段并直接 complete；`:331` 起的 `_aggregate` 再拼接 required tasks，其中还可能包含已拼接的 SYNTHESIS，导致重复输出。`task_planning.py:510` 附近会为多个任务追加 required SYNTHESIS。

触发：用户要求比较两项数值、计算差额或解释跨源差异，规划拆成两个查询任务。查询各自成功后，汇总可能只有两段材料，没有完成比较；结构状态仍为 success。

修复：统一任务主路径与证据合成器，按原始交付要求生成结论；计算使用结构化数值及单位，事实 claim 关联证据；合成不完整不得 complete；最终渲染避免重复拼接子任务和合成任务。

人工验收：M10；逐项核对最终差额、口径说明与引用，而不只看两次工具成功。

### 2. P1：依赖只检查状态，没有通用结果绑定

**代码确认**：`task_execution.py:120` 附近检查 dependencies_satisfied；`:294` 起的 `_execute_mixed_task` 仍把 `task.question` 传入执行器。没有在这里把上游实体/数值/evidence 作为下游参数输入。RAG 添加的是父问题与 expected_output，并非前一步实际结果。结构化 Web 路径有独立依赖处理，不能推广为所有任务都支持。

触发：T1 查出某基金或公司，T2 依赖 T1 再查询“该基金/公司”的指标。如果实体只能在执行时确定，T1 成功不代表 T2 已获得正确实体。

修复：给任务结果定义 typed outputs 与 input bindings，保存实体、日期、数值、单位和证据 ID；执行 T2 前解析依赖输入，解析不了则澄清/失败，不能只检查状态。

人工验收：M09，并检查下游实际 SQL/搜索输入含上游查出的实体。

### 3. P1：同一会话并发存在丢更新

**代码确认**：`entrypoint.py:457–466` 是读取 state→追加消息/压缩→set；`session_state.py` 仅提供普通 Redis get/set，无版本比较或事务保护。两个请求可以读取同一旧状态，后一次 set 覆盖前一次追加；压缩过程会扩大并发窗口。

修复：优先对同一 session 的整轮执行串行化，跨进程需 Redis 级协调；或使用带版本的 CAS/事务并处理冲突。仅给进程内字典加锁不能解决多个服务进程的竞争。

人工验收：M14，确认两个完整对话都保留，顺序和上下文一致。

### 4. P1：取消与总预算未覆盖完整主链

**代码确认**：`agent.py:84`、`:164` 使用 `asyncio.to_thread` 跑完整 Agent，finally 的 `task.cancel()` 只取消等待，不能强制停止已运行线程。`entrypoint.run` 未设置完整调用链 deadline；`TOTAL_TIMEOUT` 对应常量在 ReAct 使用，不能假设同样限制所有 requirement 执行。SQL、LLM、RAG 和结构化 Web 有各自局部预算。

触发：关闭浏览器/重复发起慢任务，后台仍可能继续外部调用或写会话；多个串行子任务累积时间可能超过用户理解的总超时。

修复：建立 run 级 deadline、取消标记及调用数量/并发预算，所有阶段读取剩余预算；可取消异步 I/O 优先，已开始的同步调用需隔离和限制资源。不能仅用 wait_for 包同步阻塞函数并宣称实现硬取消。

人工验收：M16，并观察取消后是否继续出现外部调用和会话写入。

### 5. P2：chat_history 是未兑现的接口能力

**代码确认**：`agent.py:34` 声明 chat_history，调用 `_run_agent_sync` 仅传 question/session_id/run_id。AG-UI 同样仅提取最后一条用户问题，历史消息没有直接进入上下文。

触发：客户端只传历史和“它呢？”，不复用 Redis session，接口接受请求但 Agent 缺少历史。

修复：明确选择以服务端 session 为唯一历史，删除/拒绝不支持的字段；或者实现历史标准化、上限及与 Redis 历史去重。README 已明确当前限制，业务实现尚未改。

人工验收：M17。

### 6. P2：实体与文档范围可能残留

**代码确认条件分支，影响待人工复现**：`entrypoint.py:459–461` 只在新 plan 的实体/范围非空时更新。切到无法在目录解析的新公司时，旧实体和文档范围可能仍保存；上下文构建器又读取这两个字段。完整问题通常不会继承上下文，但后续省略追问可能受影响。

修复：区分“继承原话题”“明确切换”“解析失败”，切换实体时同步重置不相容 scope，不把空值一律视作保留旧状态。

人工验收：M13，观察 Redis state 和下一轮实际检索范围。

### 7. 对外部署前优先：抓取缺少目标地址与下载体积边界

**代码确认风险面，未实施网络攻击复现**：`page_fetcher.py:81–115` 的直接抓取接受 URL、允许重定向，未在本函数检查内网/回环目标；PDF 用 resp.read、HTML 用 resp.text 完整读入后再截断。MAX_PAGE_CHARS 限制的是最终文本，不是下载字节数。

影响：模型或搜索来源给出不合适 URL 时，可能触达部署网络内的地址；大型响应也可能造成内存压力。不能把此观察表述为已成功利用的漏洞。

修复：统一抓取边界，校验协议、解析 IP 与重定向每跳，限制内网/回环/链路本地目标；流式读并按实际字节设限，同时限制解析资源。

### 8. P2 / 对外部署前优先：错误与观测接口暴露边界

**代码确认**：`agent.py:102`、`:182` 把异常原文写入回答；`debug_ui.py` 仅检查启用开关，没有用户身份/会话归属检查，提供会话读取和删除接口；`entrypoint.py:111` 直接记录问题前 200 字，不受正文开关控制。

修复：对用户返回稳定错误信息与关联 ID，详情仅留受控日志；若对外部署，增加认证和会话归属控制；统一正文/敏感字段日志策略。调试接口本机使用不等于已经验证多用户安全。

### 9. P2：复现与仓库交付不完整

**代码确认**：`page_fetcher.py:34` 可选导入 pypdf，失败时 PDF 直抓分支返回空文本，而 requirements 没有显式列它。依赖多数未固定版本。Git 工作区混有大量历史运行产物，部分临时目录无读取权限。

修复：补齐实际需要的直接依赖及可选依赖说明，整理可重现的运行资产说明与目录职责。后续调整忽略规则时仅针对确认的临时产物；不要删除数据、索引或历史结果。本次未安装依赖或清理文件。

## 进一步的 Agent 能力差距

| 改进 | 当前基础 | 建议落地方式 |
|---|---|---|
| 动态重规划 | 有局部 retry/fallback | 根据结构化缺口只修订未完成任务，限制轮次与预算，保留旧计划 |
| 跨源可信计算 | SQL rows、RAG/Web evidence | 标准化实体、时期、单位、指标，计算记录输入证据及公式 |
| 冲突处理 | 有充分性与来源记录 | 将冲突显式保存，解释采用依据或保留争议，不能靠重排分数决定事实 |
| 执行持久化 | Redis 会话、JSONL Trace | 若要长任务，保存任务状态与可恢复检查点；会话记忆不等于任务恢复 |
| 可控工具调用 | 工具注册、SQL 只读 | 把来源许可、预算与取消作为各执行器共享约束，避免路径间行为漂移 |
| 人工质量闭环 | 有调试 UI | 采用人工表逐项复核，保留失败与修复前后证据，不继续扩大自动 judge 工程 |

另一个待核查点：`task_execution.py:_source_projection` 使用汇总计划中的公司和文档范围投影到单任务；多实体任务需要人工确认 scope 是否过宽。这里先列为风险，不认定所有多实体查询都出错。
